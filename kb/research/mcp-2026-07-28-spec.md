# MCP 2026-07-28: stateless Streamable HTTP and authorization

Read from the spec source (`modelcontextprotocol/modelcontextprotocol`, HEAD `1155ca4`,
2026-10-17; `schema/2026-07-28/schema.ts` is the source of truth) and checked against the
published pages. Consequences for tab-mcp are marked **tab-mcp:**.

## Transport (Streamable HTTP)

- One MCP endpoint, POST only. GET and DELETE: `405 Method Not Allowed`. `Mcp-Session-Id`
  and `Last-Event-ID` are ignored; the server never mints or echoes a session id.
- The server MUST validate `Origin`; an invalid one gets `403`.
- Each POST body is exactly one JSON-RPC request or notification. No batching. Clients
  never POST responses.
- `Accept` must list `application/json` and `text/event-stream`. A request is answered
  either with one JSON object (`application/json`) or an SSE stream (`text/event-stream`).
  Accepted notifications get `202` with no body.
- On an SSE response the server may send `notifications/progress` and
  `notifications/message` for that request before the final response, never requests.
  The final response ends the stream. `X-Accel-Buffering: no` is recommended; keep-alive
  comment lines (`:`) are encouraged. Streams are not resumable.
- **Cancellation over HTTP is the client closing the response stream.** The server should
  stop work and send nothing more for that request. `notifications/cancelled` is stdio-only
  (servers use it only to end a `subscriptions/listen`).
- Required headers on every POST: `MCP-Protocol-Version` (must equal
  `_meta["io.modelcontextprotocol/protocolVersion"]`), `Mcp-Method` (= `method`), and for
  `tools/call`, `resources/read`, `prompts/get` also `Mcp-Name` (= `params.name`/`uri`).
  Values that are not header-safe are sent as `=?base64?…?=`. A missing header or a
  header/body mismatch: HTTP `400` with JSON-RPC `-32020` (HeaderMismatch). Tools may mark
  a primitive input property with `"x-mcp-header": "Region"`, which the client mirrors as
  `Mcp-Param-Region`; a server that reads the body must check it matches.
- **tab-mcp:** the relay parses the body anyway (to route and to answer `server/discover`
  errors), so it performs the header validation itself. Tab tools must not use
  `x-mcp-header` in version 1 (the relay would have to validate it; nothing needs it).

## Per-request metadata and statelessness

- Every request carries in `params._meta`: `io.modelcontextprotocol/protocolVersion`
  (required), `io.modelcontextprotocol/clientCapabilities` (required, `{}` allowed),
  `io.modelcontextprotocol/clientInfo` (should). Missing required fields: `-32602`, HTTP 400.
- Results should carry `_meta["io.modelcontextprotocol/serverInfo"]` and a required
  `resultType`: `"complete"` or `"input_required"`.
- Servers must not rely on earlier requests for version, capabilities or identity.
  `clientInfo` is self-reported and never a security input.
- Error codes: `-32020` HeaderMismatch, `-32021` MissingRequiredClientCapability (with
  `data.requiredCapabilities`), `-32022` UnsupportedProtocolVersion (with
  `data.supported` and `data.requested`). Unknown method: `404` plus `-32601`. Application
  errors use codes outside `-32768..-32000`.

## server/discover

Servers MUST implement it. It replaces the `initialize` result:

```json
{"resultType":"complete","supportedVersions":["2026-07-28"],
 "capabilities":{"tools":{"listChanged":true}},
 "_meta":{"io.modelcontextprotocol/serverInfo":{"name":"…","version":"…"}},
 "instructions":"…","ttlMs":3600000,"cacheScope":"public"}
```

**tab-mcp:** the tab answers it (its name, version, instructions), the relay forwards it
like any other request.

## Rejecting old clients

A 2026-07-28-only server answers an `initialize` POST with HTTP 400 and a JSON-RPC error
that names the versions it supports; "legacy clients have no fall-forward mechanism". Use
`-32022` with `data.supported: ["2026-07-28"]` when an older version is declared, `-32020`
when the modern headers are missing. The order of checks is not fixed by the spec.

## Subscriptions (list changes)

`subscriptions/listen` replaces the GET stream. The client POSTs
`{"method":"subscriptions/listen","params":{"notifications":{"toolsListChanged":true}}}`;
the server answers with a long-lived SSE stream whose first message is
`notifications/subscriptions/acknowledged` (the subset honoured, and
`_meta["io.modelcontextprotocol/subscriptionId"]` = the listen request's id). Each later
notification, e.g. `notifications/tools/list_changed`, carries that id. The client ends it
by closing the stream; a graceful server close sends a final `result` first.

**tab-mcp:** the relay holds listen streams per tab session and fans out a
`tools/list_changed` signal from the tab. That is the one place where the relay keeps a
long-lived HTTP response.

## Multi round-trip requests (MRTR)

Instead of server-to-client requests, `tools/call` may return
`{"resultType":"input_required","inputRequests":{…},"requestState":"…"}`; the client
retries with a new id, adding `inputResponses` and the echoed `requestState`. Only for
capabilities the client declared (e.g. `elicitation`). `requestState` is attacker-controlled
and must be integrity-protected if it matters.

**tab-mcp:** not needed in version 1 (confirmation of consequential tools happens in the
page, not in the AI app). The relay passes such results through untouched if a tab returns
them.

## Caching and pagination

`ttlMs` and `cacheScope` (`public` | `private`) are MUST on `server/discover`,
`tools/list` and other list results. `private` caches must not be shared across
authorization contexts. A `list_changed` notification invalidates the cache. No ETags.
Pagination uses an opaque `cursor`/`nextCursor`.

**tab-mcp:** a tab's tool list is per token, so `cacheScope: "private"` and a short
`ttlMs` (e.g. 60 000).

## Tools

- `tools/list` result: `tools`, `nextCursor?`, `ttlMs`, `cacheScope`. Order should be
  deterministic. Tool: `name` (1–128 of `[A-Za-z0-9_.-]`), `title?`, `description?`,
  `inputSchema` (`type: "object"`, JSON Schema 2020-12), `outputSchema?`, `annotations?`.
- `tools/call` result: `content[]` (text, image, audio, resource_link, resource),
  `structuredContent?`, `isError`. Unknown tool: `-32602`; execution failure: `isError: true`.
- `ToolAnnotations`: `title`, `readOnlyHint`, `destructiveHint`, `idempotentHint`,
  `openWorldHint`. There is no `consequentialHint` or `untrustedContentHint` in MCP;
  proposals for trust annotations (SEP-1913, SEP-1984, SEP-1487/1560/1561) are open.

## Authorization

Split into four pages (overview, server discovery, client registration, security).

- MCP server: RFC 9728 protected-resource metadata (PRM) with `authorization_servers`;
  advertised by `WWW-Authenticate: Bearer resource_metadata="…", scope="…"` on 401 and/or
  the well-known URL. Endpoint `https://host/mcp` → PRM at
  `https://host/.well-known/oauth-protected-resource/mcp`; clients fall back to the root
  form.
- AS metadata: RFC 8414 or OIDC discovery; clients try
  `/.well-known/oauth-authorization-server` then `/.well-known/openid-configuration`
  (path-inserted forms for issuers with a path). `issuer` must equal the URL's issuer.
- Client registration priority in clients: pre-registered, then **CIMD** (if the AS
  advertises `client_id_metadata_document_supported: true`), then DCR (deprecated in
  2026-07-28 but still MAY), then asking the user.
- CIMD on the AS: fetch the HTTPS `client_id` URL, check the document's `client_id` equals
  the URL, required fields `client_id`, `client_name`, `redirect_uris`; validate the
  request's `redirect_uri` against `redirect_uris` exactly; cache per HTTP headers; guard
  against SSRF; show the redirect host clearly; warn on localhost-only redirect URIs.
- PKCE is mandatory; clients refuse an AS without `code_challenge_methods_supported`.
  Advertise `["S256"]`.
- `resource` (RFC 8707) is sent in the authorization and token requests with the canonical
  MCP URI; the server MUST validate the token audience and reject other tokens. Bearer only
  in the `Authorization` header.
- New in 2026-07-28: the AS SHOULD return `iss` (RFC 9207) in authorization responses and
  then MUST advertise `authorization_response_iss_parameter_supported: true`; refresh-token
  guidance (rotate for public clients); DCR `application_type`; credentials bound to issuer.
- Errors: 401 invalid/missing token, 403 `insufficient_scope`, 400 malformed.
- Exact redirect-URI matching, `state`, no token passthrough.
