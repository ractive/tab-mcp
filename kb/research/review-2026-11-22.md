# Website, code and wording review of tab-mcp, 2026-11-22

The owner asked for all tab-mcp pages on ractive.ch to be read and checked for
understandability and coherence, followed by a code review and a comparison of the
wording and behaviour in the repository and on the website.

The site is understandable for developers, but it is not fully coherent with the
current implementation. The main problems are misleading access-status wording,
documentation that describes older behaviour, and four reproducible code issues.

## Scope and method

- **Repository:** commit `09704a2`. Reviewed the relay, client library, extension and
  accompanying documentation. Code references below refer to that revision.
- **Website:** read all five pages under `/tab-mcp/` listed in the live sitemap:
  [overview](https://ractive.ch/tab-mcp/),
  [connection guide](https://ractive.ch/tab-mcp/connect/),
  [privacy](https://ractive.ch/tab-mcp/privacy/),
  [diagram example](https://ractive.ch/tab-mcp/examples/diagram/) and
  [todo example](https://ractive.ch/tab-mcp/examples/todo/).
  Also read the linked [sign-in example](https://tab-mcp-login.ractive.ch/) and
  [Saturnus overview](https://ractive.ch/saturnus/).
- **Freshness:** the web reader initially returned an older cached homepage. The
  findings use the live pages fetched directly on 22 November, not that cached copy.
- **Browser check:** inspected the rendered todo example and the WebMCP tools exposed
  by the browser. No tool that changes the example's data was called.
- **Reproductions:** exercised the schema transformation, pending approval, output
  schema compilation and generated shell command paths in temporary scripts outside
  the repository.
- **Verification:** ran `bun run verify` and checked internal fragment links among the

## Reproduced code issues

### 1. [P2] A changed tool can retain approval given for its previous description

The extension's `sameTool` comparison checks the tab, document, name, origin and
read-only flag, but ignores the title, description, schema and consequential hint.

**Reproduction:** start a call whose confirmation describes “Save a draft only”. While
that confirmation is pending, change the tool to “Publish the draft publicly”, change
its consequential hint, and refresh the bridge's tool list. Keep the document, tool
name and read-only flag unchanged. Allowing the original question still lets the call
proceed. The reproduction used `PageToolBridge.callByName` and recorded one call after
the change.

Approval should be invalidated when the offered tool definition changes. This concerns
the consistency of a pending approval with a changed definition; it is not a claim that
tool descriptions can make an untrusted page trustworthy.

**Code:** [bridge.ts](../../packages/tab-mcp-extension/src/worker/bridge.ts),
`sameTool` at line 471 and the post-confirmation check at line 655.

### 2. [P2] Removing regular expressions can make valid arguments invalid

The extension removes `patternProperties` but preserves
`additionalProperties: false`. A schema allowing keys matching `^x-` consequently
becomes one allowing no keys.

**Reproduction:** this schema accepts `{"x-name":"Alice"}`:

```json
{
  "type": "object",
  "patternProperties": { "^x-": { "type": "string" } },
  "additionalProperties": false
}
```

`schemaFor()` transforms it into
`{"type":"object","additionalProperties":false}`, which rejects those same
arguments. Both validation outcomes were checked.

The transformation needs to preserve permissiveness while avoiding execution of
untrusted regular expressions.

**Code:** [bridge.ts](../../packages/tab-mcp-extension/src/worker/bridge.ts),
`withoutPatterns` at line 190.

### 3. [P2] Output schemas do not receive the validation promised by the README

The [client README](../../packages/tab-mcp-client/README.md), at line 124, says
`outputSchema` is checked like `inputSchema`, but the compilation step only examines
the input schema.

**Reproduction:** an output schema with a nested `$id` and an unresolved relative
`$ref` survives registration and `compileRegistry()` with no errors:

```json
{
  "type": "object",
  "$defs": { "s": { "type": "string" } },
  "properties": {
    "a": { "$id": "https://y.example/t", "$ref": "#/$defs/s" }
  }
}
```

The same schema is rejected as input. The bundled MCP client's Ajv validator also
rejects it. The library can therefore advertise a tool whose output schema prevents a
client from calling it.

Apply the corresponding schema-compilation checks to output schemas as well. This is
separate from validating tool results against their schemas, which the README explicitly
says the library does not do.

**Code:** [mcp.ts](../../packages/tab-mcp-client/src/mcp.ts), `compileTool` at line 112.

### 4. [P2] Generated setup commands fail for IPv6 addresses in zsh

`commandAddress()` treats square brackets as safe without quoting. For an IPv6
loopback address, the setup instructions generate:

```sh
claude mcp add --transport http test http://[::1]:8080/s/test/mcp
```

**Reproduction:** passing the unquoted address to `print` under `zsh -fc` fails with
`no matches found: http://[::1]:8080/s/test/mcp`, before the command runs. The problem
is shell expansion, independent of the MCP client.

Quote addresses appropriately, or use the existing instruction-only fallback for
bracketed addresses.

**Code:** [command.ts](../../packages/tab-mcp-client/src/command.ts),
`commandAddress` at line 33.

## Website and documentation inconsistencies

### 5. “AI access: Off” overstates what has been disabled

On the rendered [todo example](https://ractive.ch/tab-mcp/examples/todo/), the page
showed “No AI app can use this page” while the browser exposed all four WebMCP tools.
The [diagram example](https://ractive.ch/tab-mcp/examples/diagram/) uses the same
wording. The status describes the relay connection, not all AI access.

A clearer label would be **“Relay connection: Off”**, followed by:

> AI apps cannot reach this page through the relay. Browser agents can still use its
> WebMCP tools.

### 6. The hosted privacy notice omits newer extension behaviour

The [published notice](https://ractive.ch/tab-mcp/privacy/) lacks the handshake and
“Fill in the code for me” disclosures already present in
[the extension's privacy document](../../packages/tab-mcp-extension/PRIVACY.md), from
line 34.

Participating pages can learn connected AI apps' names and verified hosts. Code filling
reads connection-form metadata and can remember approved hosts and recent fill times.
The hosted notice needs to describe these behaviours and qualify its statement that a
page does not learn which AI app is connected.

Additionally, **both notices' storage inventories omit the cached connected-app list**
persisted by `saveGrants()`: grant ids, names and hosts. See
[settings.ts](../../packages/tab-mcp-extension/src/worker/settings.ts), lines 54–70.
These inventories should match the implementation. This finding concerns factual
consistency with the code, not a legal assessment of the notices.

### 7. Browser requirements differ between the website and repository

The [homepage](https://ractive.ch/tab-mcp/#webmcp) describes the extension-provided
WebMCP fallback and a Firefox build awaiting review. The
[root README](../../README.md), at lines 59–85, still requires Chrome with WebMCP
enabled and later says there is no Firefox extension. The
[extension README](../../packages/tab-mcp-extension/README.md) also retains
native-WebMCP-only wording.

Distinguish browser capability, extension capability and store availability
consistently. A Firefox build existing and a Firefox store release being available are
different claims.

### 8. The security policy describes an older WebMCP exposure rule

[SECURITY.md](../../SECURITY.md), at lines 51–56, implies an additional opt-in for
tools that change state. Current code mirrors every registered tool when
`webmcp: true`, unless `callers` excludes WebMCP. Confirmation then follows the tool's
annotations.

The current client README explains this change; the security policy should say the
same. See [webmcp.ts](../../packages/tab-mcp-client/src/webmcp.ts), from line 101.

### 9. The homepage's compatibility claim is too broad

“Any other MCP client” on the [homepage](https://ractive.ch/tab-mcp/) conflicts with
the repository's explicit requirement for MCP revision `2026-07-28` and CIMD,
including its unsupported-client list.

Replace it with **“a compatible MCP client”** and link
[compatibility](../../docs/compatibility.md) near the introduction. This is a mismatch
between the project's own claims; the review did not independently retest every
third-party AI app's current release.

## Readability and wording

| Page | Assessment |
|---|---|
| [Overview](https://ractive.ch/tab-mcp/) | Explains the architecture accurately in most places, but introduces MCP, WebSocket, relay and client before explaining “tool”. Put the concrete tool definition earlier and offer separate starting points for users and site authors. |
| [Connection guide](https://ractive.ch/tab-mcp/connect/) | The clearest page. The address/code distinction is useful. Its opening “Every AI app needs…” should qualify that account-based connections use sign-in instead of a code. |
| [Diagram example](https://ractive.ch/tab-mcp/examples/diagram/) | The example prompts make the purpose clear. The editor instructions are a dense paragraph; separate mouse actions, keyboard shortcuts and undo behaviour. |
| [Todo example](https://ractive.ch/tab-mcp/examples/todo/) | Concrete and approachable. The incorrect “Off” status is its main comprehension problem. |
| [Privacy](https://ractive.ch/tab-mcp/privacy/) | Clearly separates relay and extension responsibilities, but needs the factual updates above. |

Two smaller wording points on the overview:

- **“Without a backend”** needs an immediate qualification that a relay server is
  still required.
- **“Only the person in front of the tab”** should describe possession of the code
  rather than imply proof of physical presence.

Conversely, **“Always allow all” versus “Always allow everything” is an intentional,
meaningful distinction** in [the wording glossary](../design/wording.md) and should
remain. The extension covers currently listed tools on a site; the library's
“everything” also covers future and changed tools for that connected AI app.
