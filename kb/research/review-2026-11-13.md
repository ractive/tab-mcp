# Full review of tab-mcp, 2026-11-13

The owner asked for a full review of every component: security, code quality, UX/UI, how
WebMCP is integrated, and what is overengineered and could be simpler. Eight reviewers
(Claude Fable 5.2 agents, each in a fresh context with its own scope) read the code; none
changed anything. Their reports follow below unshortened. This head is the triage.

## How it was done

- **Tree.** `main` plus iteration 28 as it stood before the review fixes of PR 114, and
  the ractive.ch checkout (branch `tab-mcp/overview-opt-and-tools`, client 0.13.1 to
  0.14.0). Line numbers refer to that state.
- **Method.** Read-only. Every finding says whether its code path was read end to end
  (confirmed) or not (plausible). Nothing was run in a browser; the relay reviewers ran
  two one-line checks of Bun's timer and SQLite behaviour. Each reviewer checked the
  decision log before calling something a defect; owner decisions are listed as
  proposals, not defects.
- **Spot checks by the session that collected the reports** (code read again): EQ 1,
  ES 2, CC 2 and RQ 1 hold as described.
- **The reports** below are the reviewers' own text, written to files by them and joined
  here without changes. The WebMCP reviewer fetched the draft and Chrome's documentation
  on 2026-11-13 (see Citations).
- **Ids.** RS relay security, RQ relay code quality, CC client core, CU client UI and
  API, ES extension security, EQ extension quality and UX, WM WebMCP, EX examples; the
  number is the finding's number in that report.

## The picture in short

- **No finding lets a stranger call a page's tools, read a token or forge a caller.** The
  OAuth core, the SSRF defences, token handling, the tunnel's header filtering, the
  confirmation path, the extension's message senders and the examples' handling of
  AI-supplied text were all read and found sound (each report ends with what it found
  sound).
- **The relay's open issues are denial of service by an unauthenticated party** (RS 1 to
  4) and one correctness bug that costs a user their pairing (RQ 1).
- **tab-mcp for Chrome has the most work left**, which fits its state (0.1.0, not yet in
  the store): one high finding (EQ 1), tools that silently break (ES 2), a bridge that
  can hang (ES 1), a panel that states the wrong connection state (EQ 3), and a store
  listing that predates the navigation tools (ES 3).
- **The client's confirmation, the one run-time brake, has three gaps**: a hint that is
  not a boolean fails open (CC 2), two stacked confirmations can be approved with a
  double click (CU 1), and the arguments can hide a field below the fold (CU 2).
- **WebMCP: the draft moved** (`outputSchema`, WM 3), two representations are not mapped
  cleanly (WM 4, WM 6, WM 12 / CC 3), and the dedupe between the mirror and the
  extension hides tools it should not (WM 1).
- **One live bug loses user data**: the diagram example writes coordinates its own
  loader rejects (EX 1).
- **Overengineering**: the reviewers name roughly 2 800 lines of source (plus tests) that
  could go. The larger ones touch decisions and are listed under
  [Simplification](#simplification-for-the-owner-to-decide).

## Fix first

Ordered by what goes wrong for a user or operator today.

1. **EX 1, live:** the diagram editor loses the diagram on reload after `layout` (28
   unconnected shapes or a chain of 40 are enough). ractive.ch, small fix in `model.ts`.
2. **RQ 1:** a token store failure during a refresh answers "try again", and the retry
   revokes the grant. Reorder `markUsed` and `issueTokenPair`.
3. **EQ 1 (high):** `webmcp_tools` returns no input schemas, so `webmcp_call` is

4. **ES 2:** a page tool with a parameter named `pattern` loses it and can become
   uncallable.

6. **CU 1, CU 2:** stacked confirmations and arguments below the fold.
7. **RS 1 to RS 4:** four cheap ways for an unauthenticated party to stop pairing or
   park sockets on the hosted relay.
8. **ES 1:** a page that does not answer blocks the extension's bridge for every tab.
9. **RQ 3:** a session lifetime, heartbeat or timeout above 24.8 days fires at once; a

# The reports

## Relay: security

Relay security review (`packages/tab-mcp/src/**`): 20 findings, none high, 4 medium (all cheap denial of service by an unauthenticated party), 16 low.

Everything was read, nothing was run. "Confirmed" means I followed the code path end to end; where the outcome also depends on Bun or browser behaviour I did not test, the finding says so.

### 1. Findings

#### 1. The global cap of 10 000 open authorization requests can be filled by one party; then nobody can pair

- Where: `packages/tab-mcp/src/oauth/server.ts:63-68`, `:735-743`
- Severity: medium
- Kind: security
- Confidence: confirmed
- `GET /authorize` answers 429 for everyone once `#pending.size >= MAX_PENDING`. The per-IP share is 10 and IPv6 counts per /64, so one /48 (65 536 /64s) supplies the 1 000 networks needed. Pending requests survive their session: nothing drops them when the tab closes. The attacker opens a session with an allowed (forgeable) `Origin`, sends `hello` and `pairing.start`, makes 20 GETs from 4 /64s, closes, and repeats with a new secret: about 500 WebSocket handshakes and 10 000 GETs every 10 minutes. DEC-088 says the total cap "only affects the network that fills them"; that is wrong for the total.
- Suggested change: when the total is full, evict instead of refusing (first the requests of addresses with no connected session or a closed dialog, then the oldest of the network holding the most). Drop an address's requests about 60 s after its session ended. Count the per-network share by /56 or /48 as `ipSessionKeys` does.

#### 2. About 1.2 requests a second keep the "new client" metadata budget empty: no uncached AI app can pair

- Where: `packages/tab-mcp/src/oauth/cimd.ts:223`, `:372-398`; reached from `oauth/server.ts:636` and `:1367`
- Severity: medium
- Kind: security
- Confidence: confirmed
- The overall bucket for unknown client ids is 30, then 1/s. A fetch is charged before it runs, a failed one too, and the client id can name any third-party host. Made-up paths on five or six hosts across two or three registrable domains stay inside the per-host (0.2/s) and per-domain (0.6/s) shares and take every global token. Through `/token` with a junk `client_assertion`, one IP is enough: its ceiling is 20/s, and the resulting 503s are not counted as failures. After every restart the cache is empty, so every AI app is "new" and gets "The relay is busy"; `private_key_jwt` clients also get 503 on refresh. DEC-089 fixed the wildcard-subdomain variant only; threat model A3 "What is left" does not name this. A relay with `TAB_MCP_CLIENT_ID_HOSTS` set is immune.
- Suggested change: charge the requester for causing uncached fetches (for example 5 per IP prefix, then 1/min, at `/authorize` and `/token`) before the global bucket. Recommend `TAB_MCP_CLIENT_ID_HOSTS` in the self-hosting guide and state the residual in A3.

#### 3. Tab control messages have no rate limit; a `grants.revokeAll` flood runs store writes on the event loop

- Where: `packages/tab-mcp/src/session.ts:339-346`; `relay.ts:486-498`; `store/sqlite.ts:239-258`; `docs/protocol.md:334` (`rate_limited` "not sent yet")
- Severity: medium
- Kind: security
- Confidence: confirmed (the code path); the size of the stall is plausible, not measured
- Every `grants.revokeAll` frame (27 bytes) runs `listGrants`, a SQLite write transaction and `auth.addressRevoked`, which scans up to 10 000 pending requests and 10 000 codes. bun:sqlite is synchronous, so all of it runs on the main thread. One socket can send tens of thousands of these per second, and it needs only an allowed `Origin`, which a program can forge. `grant.revoke` (one SELECT per frame) and `identity` (JWT decode, possibly a signature check, an unbounded promise chain in `#identityChain`) are unthrottled too. Every HTTP path has a per-IP limit; this one has none.
- Suggested change: a token bucket per session for everything except `pong` and `http.response*` (for example 30, then 2/s), closing with the reserved 4008. Make `grants.revokeAll` a no-op while the address tombstone is younger than a second.

#### 4. `/token`, `/revoke` and `POST /authorize` read their body without a deadline

- Where: `packages/tab-mcp/src/oauth/server.ts:1123-1129` (`#readForm`); compare `relay.ts:924-949`
- Severity: medium
- Kind: security
- Confidence: confirmed that the deadline is missing; the Bun behaviour is DEC-048's own measurement (Bun 1.4.3), which I did not re-run
- DEC-048 says Bun's `idleTimeout` does not fire while a handler waits for an unfinished body, which is why MCP bodies have their own 10 s deadline. `#readForm` awaits `req.arrayBuffer()` bare. A client that sends headers with `Content-Length: 100` and then stalls holds the socket and the handler for as long as it keeps the connection open. `/token` admits 600 at once and then 20/s per IP prefix before the read, so one host can park about 72 000 sockets an hour. A proxy that buffers request bodies (nginx by default) absorbs this; a directly exposed relay, or a proxy that streams bodies, does not.
- Suggested change: move the deadline race out of `readBody` into one helper used by both, answering 408 with `Connection: close`.

#### 5. A client's JWKS may hold hundreds of keys under one `kid`; each junk assertion is verified against all of them

- Where: `packages/tab-mcp/src/jwt.ts:376-407`; `oauth/cimd.ts:355-364`; `oauth/server.ts:1790-1801`
- Severity: low
- Kind: security
- Confidence: confirmed (no cap); the CPU cost is plausible, not measured
- Anyone can publish a client document with a 64 KiB JWKS: about 800 Ed25519 keys sharing one `kid`. `verifyJwt` imports and verifies every candidate, so a 1 KB `/token` request with a random signature costs about 800 `importKey` plus `verify` calls. `#tokenFailuresPerIp` does not stop it: it only turns the answer into 429 after the work is done. Only the 20/s ceiling per /64 bounds it.
- Suggested change: keep at most about 20 keys per set in `JwksCache.#refresh` and try at most 3 candidates per `kid`. Check the failure bucket (`available`) before client authentication, so a drained network is refused before the work.

#### 6. On an open relay the page origin is arbitrary, unbounded text, shown at `/authorize` and logged

- Where: `packages/tab-mcp/src/relay.ts:821-868`; `oauth/server.ts:1182-1188`; `session.ts:482-488`
- Severity: low
- Kind: security
- Confidence: confirmed
- With `TAB_MCP_ALLOWED_ORIGINS=*`, `siteFor` accepts any `Origin` value and `handleTab` stores it raw. A program can send `Origin: https://ractive.ch (verified by the relay)`, or 8 KB of text. The pairing page shows it in the origin slot (escaped) and `tab.session` logs it. A11 concedes that a program can claim any origin, but not free text. A7 says every shown value is "length-limited", which is false here.
- Suggested change: on an open relay accept only a serialised origin (`new URL(o).origin === o`, at most 255 characters, or an extension origin). Treat anything else as no origin.

#### 7. The page's app name keeps bidi and invisible characters and may carry a look-alike origin; client names are cleaned, app names are not

- Where: `packages/tab-mcp/src/config.ts:363-373` (`isAppName`); shown at `oauth/server.ts:1189-1192`; sent to the model in `notopen.ts:44-51`
- Severity: low
- Kind: security
- Confidence: confirmed (the missing filter); the rendering effect is plausible
- `displayName` and `foreignDomain` (DEC-065, DEC-092) protect the pairing page from client names. `hello.app.name` is checked only for C0/C1 controls. A page on any listed origin can send `saturnus on https://ractive.ch` plus U+202E. It is rendered in `<strong>` with no bidi isolation, directly before the real origin, which the override then reverses. The same string is placed in relay-authored text for the model ("Ask the user to open …", and `instructions` in the `server/discover` stand-in) and is kept in `lastSeen` after the page closed.
- Suggested change: pass `app.name` through `displayName()` and refuse names that contain a domain other than the session origin's host, as for clients. Add `unicode-bidi: isolate` to the `strong` and `.origin` rules.

#### 8. The MCP endpoint reads and parses up to 1 MiB before it looks at the token, with no per-IP limit

- Where: `packages/tab-mcp/src/relay.ts:1074-1125`
- Severity: low
- Kind: security
- Confidence: confirmed
- DEC-040 fixes the order of the answers (version errors before 401), but the cost follows it too. A request with no or a junk `Authorization` gets its whole body buffered, decoded, `JSON.parse`d and, with a well-formed bearer, one store read. This is the only endpoint without a per-IP bucket (deliberately, for shared AI app egress), so the work is bounded only by bandwidth.
- Suggested change: keep the answer order but cap the body at `MIN_MESSAGE_BYTES` (16 KiB) unless the bearer already authenticated. Look the token up first and decide the limit from the result; version probes are small.

#### 9. Three /64s, not "many networks", lock the owner out of typing the code

- Where: `packages/tab-mcp/src/oauth/server.ts:310-326`, `:937-947`; `docs/threat-model.md:67-69`
- Severity: low
- Kind: docs
- Confidence: confirmed
- The per-address bucket is 30, then one every 30 s; the per-address-and-network share is 10, then one a minute. Three /64s drain it and two keep it drained. One residential /56 has 256 of them. The owner's correct code is then refused unjudged ("Too many attempts for this page") while the dialog is open. DEC-061 accepts the trade for "an attacker with many networks"; the real bar is one IPv6 subscriber who knows the address.
- Suggested change: key `#guessesPerAddressIp` by /56 for IPv6 (as sessions are), and say "three networks" in A1.

#### 10. Whoever knows an address can watch whether the page is open and its dialog is up, and read its origin and app name

- Where: `packages/tab-mcp/src/oauth/server.ts:705-717`, `:825-847`, `:1182-1192`
- Severity: low
- Kind: docs
- Confidence: confirmed
- `GET /authorize` with any valid client and the address as `resource` gives three distinguishable answers: "Open the page first" (no session), "Open 'Connect your AI app' first" (session, dialog closed), or the pairing page with the page's origin and app name. A1 says the address alone grants nothing and that addresses look the same without a token. That holds for `/a/{id}/mcp`, not for `/authorize`.
- Suggested change: use one text for the two offline cases (the retry is the same anyway), and note the remaining presence signal in A1.

#### 11. Identity binding checks that the dialog is open when Connect is clicked, not when the provider returns

- Where: `packages/tab-mcp/src/oauth/oidc.ts:253-260` against `:398-425`
- Severity: low
- Kind: security
- Confidence: confirmed
- `check()` requires `target.pairingOpen`; `callback()` compares only the identity. A sign-in started while the dialog was open pairs up to 10 minutes after the user closed it. With codes, `pairing.stop` voids the code at once. A12's "the dialog must be open, as with codes" is therefore weaker than it reads.
- Suggested change: in `callback()`, fail with reason `inactive` when `!target.pairingOpen`, before the identity comparison.

#### 12. `identity_refused` passes internal error text to the tab

- Where: `packages/tab-mcp/src/relay.ts:554-559`; `jwt.ts:379-383`, `:195-230`
- Severity: low
- Kind: security
- Confidence: confirmed
- For `jwks_unavailable` the tab gets "the signing keys could not be loaded: " plus the inner error's message. That is `fetchJson`'s text with the configured assertion JWKS URL and HTTP status, or Bun's raw fetch error. Any program with a listed `Origin` on an `oidc` site can trigger it with an unknown `kid`. `/token` deliberately answers one fixed text for the same condition.
- Suggested change: send a fixed message per `JwtError.reason` to the tab and keep the detail in the log.

#### 13. The metadata fetch's 5 s timeout does not cover the DNS lookup

- Where: `packages/tab-mcp/src/oauth/cimd.ts:126-129`, `:496-504`
- Severity: low
- Kind: security
- Confidence: plausible (resolver timing not tested)
- `#vettedAddress` awaits `Bun.dns.lookup` with no deadline. A client id on a domain whose name server never answers holds the `/authorize` or `/token` request for the system resolver's timeout, and holds a resolver slot that JWKS and provider fetches share. A3 states "a 5 second timeout".
- Suggested change: race the lookup against the same `AbortSignal.timeout`, failing as `unresolvable`.

#### 14. Worst-case memory in flight is about 10 GiB at the defaults

- Where: `packages/tab-mcp/src/relay.ts:1586-1588`; `exchange.ts:409-419`; `config.ts:161-178`
- Severity: low
- Kind: security
- Confidence: confirmed (the arithmetic); plausible in practice
- Per session: 4 MiB of WebSocket send buffer towards a page that does not read. Per exchange (8 per session): a 1 MiB request body, its parsed copy (both held by the `handleMcp` closure) and up to 1 MiB of queued response. With 500 sessions that is roughly 500 × 20 MiB. It needs about 100 networks, each with its own page and grant. The waiting queue was bounded to "a few MiB" on purpose (16 KiB bodies only); the forwarded path was not.
- Suggested change: stop holding `body.value` after admission (keep only method and id), and either lower `backpressureLimitBytes` to twice `maxMessageBytes` or state the bound in the self-hosting guide so containers are sized for it.

#### 15. `X-Real-IP` / `X-Forwarded-For` values are used verbatim as limiter keys when they are not a bare IP

- Where: `packages/tab-mcp/src/relay.ts:773-786`; `ip.ts:139-143`
- Severity: low
- Kind: security
- Confidence: confirmed (the code); plausible (which proxies do this)
- Proxies that append the port (`203.0.113.7:51234`; Azure Application Gateway does this in `X-Forwarded-For`) produce a value neither parser accepts. `ipPrefixKey` returns it unchanged, so every connection gets its own key and every per-IP limit, sessions included, stops limiting. The log shows `?`, so it goes unnoticed.
- Suggested change: strip a `:port` or `[v6]:port` suffix. If the value still does not parse, fall back to the socket address and warn once.

#### 16. Keep-alive comments are written into streamed bodies that are not event streams

- Where: `packages/tab-mcp/src/exchange.ts:464-479` (with `:245`, `:156`)
- Severity: low
- Kind: correctness
- Confidence: confirmed
- A tab may answer a non-listen request with `http.response.start` and any content type. `#scheduleKeepAlive` then writes `: keep-alive\n\n` whenever `#atBoundary` is true, which it is before the first chunk and after any chunk ending in a blank line. #### 17. The visit cookie is not renewed, so a second authorization within 10 minutes can fail with "your browser may block cookies"

- Where: `packages/tab-mcp/src/oauth/server.ts:1100-1115`, `:887-900`
- Severity: low
- Kind: ux
- Confidence: confirmed
- `#browserId` sets the cookie (Max-Age 600) only when it is absent. A request opened at minute 9 of an earlier visit has a 10-minute form whose cookie expires after one minute. The post then arrives with a fresh cookie and is refused with a message that blames the browser.

#### 18. `form-action` gets an IPv6 literal for `http://[::1]:port` redirects, which CSP source lists do not accept

- Where: `packages/tab-mcp/src/oauth/server.ts:248-257`; `oauth/cimd.ts:875`
- Severity: low
- Kind: correctness
- Confidence: plausible (browser behaviour not tested)

#### 19. `private_key_jwt` is about 550 lines and a second attacker-driven fetch path, for a client that also lists `none`

#### 20. The "anyone can be a client" defences exist only because the client host list is open by default

- Kind: simplification
- Confidence: confirmed

Lost: self-published clients work only where the operator opts in. This touches DEC-006 and DEC-100 (owner), so it is a proposal, not a defect.

### 2. Could be deleted or simplified

- `private_key_jwt` end to end (finding 19): about 550 lines plus tests and three paragraphs of the threat model.
- `DomainCache`, the three fetch budgets, the failure cache and the name heuristics, given a default client host list (finding 20): about 250 lines.
- `#usedRequests`, `#usedPage`, `#rememberUsed`, `#sweepUsed`, `#usedRequest` (`oauth/server.ts:149-156`, `:507-531`, `:1820-1862`, about 75 lines): a 10 000-entry map and a second CSRF check only to say "already connected" instead of "expired or already used" on a double submit. The generic text already covers it.
- `CloseCode.rateLimited` and the `rate_limited` error code: implement them (finding 3) or remove them from the protocol; reserved-but-unused reads as if a limit existed.
- One body reader with a deadline in place of `readBody`'s inline race and `#readForm` (finding 4).

### 3. Looked at and found sound

- **Authorization codes:** 256-bit, stored hashed, 60 s, single use; client id checked before the code is burned; reuse revokes; PKCE S256 only, verifier format checked, constant-time compare; exact `redirect_uri` and `resource`.
- **Refresh tokens:** atomic `markUsed`, reuse revokes the grant, another client id is refused without revoking, the `private_key_jwt` binding is checked before reuse detection, absolute grant end, tombstones checked inside `put`'s transaction.
- **Redirect URIs:** exact match, loopback port only, canonical form required; `javascript:`, `data:` and one-word schemes refused; invalid requests are shown, not redirected; `iss` is on every redirect.
- **CIMD fetch (SSRF):** https and default port only, canonical URL (no alternative IPv4 spellings), every resolved address checked, connection pinned to the vetted address with `Host` and `serverName`; `redirect: "manual"`, 64 KiB counted while streaming, content type checked, private and special ranges including mapped, NAT64, 6to4 and Teredo. Bun's fetch docs say each distinct `serverName` has its own TLS context and keep-alive pool, so a pinned connection cannot be reused across hosts.
- **JWT verification:** asymmetric algorithms only, bound to key type and curve, `jwk`/`jku`/`x5u` ignored, `crit` refused, private members stripped, claims checked only after the signature; tab assertion `typ`, `iss`, single `aud`, at most 60 s, replay per person; ID token `iss`, `aud`, `azp`, `exp`, `iat`, `nonce`; state single use and bound to the visit cookie.
- **Client assertions:** `iss` = `sub` = client id, audience, time window, `jti` claimed only after everything else passed, quota per host.
- **`/authorize` pages:** every interpolated value is escaped; CSP `default-src 'none'`, `frame-ancestors 'none'`, XFO, no scripts; CSRF token bound to the request and a `__Host-` cookie (Bun 1.4.4's `Bun.CSRF` does take `sessionId`); `Origin` and `Sec-Fetch-Site` checked; a new cookie means refusal.
- **Pairing codes:** uniform 6 digits by rejection sampling, constant-time compare, 5 attempts, stopped with the dialog and the session; the per-address cap fails closed; only well-formed guesses against a live code are charged.
- **`/tab`:** origin allow-list by exact match, subprotocol, `?a=` parsed raw and checked against the secret before anything is claimed, hello timeout, frames refused by length before parsing, binary frames refused; per-IP counters are released exactly once.
- **Takeover and `revokeAll`:** claim and revoke in one step; pending requests and codes dropped; the grant dates from its code; the revocation is remembered and checked synchronously right before the forward.
- **Identity binding across sites of one relay:** a stolen secret presented under a `code` site's origin gets no requests of subject-bound grants, and a grant it pairs is refused and revoked once the real `oidc` page binds.
- **Tunnel headers:** request allow-list plus `mcp-param-*`; `authorization`, cookies and forwarding headers are never sent to the page; from the page only `content-type` and `cache-control`, with values checked as RFC 9110 field values; status 200-599; `grant` is set by the relay.
- **SSE framing:** relay-wrapped bodies are split into `data:` lines; error events only at an event boundary; `maxBodyBytes` enforced on buffered and wrapped bodies; listen streams must be event streams. A tab-chosen `content-type` on the relay's origin cannot be navigated to, because the endpoint needs an `Authorization` header.
- **Tokens:** 256-bit, SHA-256 hashes only in the store, accepted only in `Authorization`, checked for kind, address, expiry and scope; re-checked after a wait.
- **Logging:** no bodies, tokens, codes or secrets; error names only; client hosts, not client ids; IPs truncated. One exception is finding 6.
- **Test hooks:** `createTestRelay` and the CIMD test mode are not exported from `index.ts` or `testing.ts` (nor from the built `dist` entries) and cannot be set from configuration; `NODE_ENV=development` only allows `http:` URLs.
- **Config parsing:** unknown site keys and limits are refused, origins normalised, `*` only as the whole value, `oidc` with `*` refused, https required outside development. Nothing was found that fails open.
- **Bounded state:** waiters, `lastSeen`, the revocation memory, codes, flows, rate-limiter maps, the replay caches and the `/healthz` probe are all bounded.

### 1. Findings

#### 1. A store failure during a refresh answers "try again", and the retry revokes the grant

- Where: `packages/tab-mcp/src/oauth/server.ts:1644-1683` (refresh), `:1497`, `:1529-1553` (code), `:1280-1290`
- Severity: medium
- Kind: correctness
- Confidence: confirmed (read end to end)
- `#refreshGrant` calls `markUsed` and then `issueTokenPair`. If a `put` throws in between (disk full, a network store), the error leaves `token()` as 503 `temporarily_unavailable` with `Retry-After: 10`. The client retries with the same refresh token, `record.usedAt` is set, `#reuseDetected` revokes the grant and the user has to pair again. The code grant has the same shape: `issued.used = true` and `issued.grantId` are set before `issueTokenPair`, so the retry gets "the code was already used".
- Suggested change: in the refresh, store the new pair first and call `markUsed` last (a loser of the race still ends in `#reuseDetected`, which deletes both pairs, as today). In the code grant, reset `used` and `grantId` when `issueTokenPair` throws (not when it returns `undefined`).

#### 2. `/token`, `/revoke` and `POST /authorize` read their body without the deadline MCP bodies have

- Confidence: confirmed in code; the premise (Bun's idle timeout does not fire while a body is awaited) is DEC-048's measurement, not re-measured

- Suggested change: one `readBodyWithDeadline(req, maxBytes, timeoutMs)` used by `readBody` and `#readForm` (408 and `Connection: close`). It also removes one of four bounded-body readers (finding 14).

On slow block storage that is several milliseconds of stall per refresh, at the 20 a second per network that DEC-117 allows.
- Suggested change: measure first. If it shows, `PRAGMA synchronous = NORMAL` (safe against corruption in WAL; a power loss can drop the last commits, which costs a re-pairing), and one transaction for the three deletes.

#### 20. `Bun.serve` has no `error` handler

## Client library: security and correctness

Client library (non-UI) security and correctness review: 15 findings, 3 medium, 12 low, none high. Read-only; nothing was run. All paths repo-relative.

### Findings

#### 1. `serve` never learns that its caller is gone: calls, open confirmations and listen streams outlive it

- Where: `packages/tab-mcp-client/src/serve.ts:76`, `:217-343`; `src/tunnel.ts:371-375`; `packages/tab-mcp-client/README.md:195-202`
- Severity: medium
- Kind: correctness
- Confidence: confirmed (read `servePort`, `createTunnel`, `createTunnelFetch.close` end to end)
- The port protocol has no end-of-life signal and `servePort` reacts to nothing but `close()`/`signal`. `createTunnelFetch.close()` fails its pending fetches locally and sends no `http.cancel`, so when the backend's socket drops, the page keeps running tool calls, keeps a confirmation dialog open (Allow then runs the tool for nobody) and keeps listen streams registered. The README's backend makes a tunnel per socket, so after a reconnect ids start at `t1` again: `inflight.set(msg.id, controller)` overwrites the older entry without aborting it, the old request is orphaned (signal never aborts, its listen listener stays until `handler.close()`). The README page sample drops the `ServeHandle` and calls `serve` again on every `tools-wanted`, so each chat reload leaks a handler, a registry listener and whatever was in flight.
- Suggested change: in `createTunnel.run`, abort an existing controller with the same id (or answer `bad_message`); make `createTunnelFetch.close()` send `http.cancel` for every pending id (the send is already try/caught); in `servePort` close on the port's `close`/`messageerror` event where the browser has it; in the README keep the handle and close the previous one before serving again, and say that the page must `close()` when the channel drops.

#### 2. A `consequentialHint` that is not a boolean is dropped silently, so the tool runs without a question

- Where: `packages/tab-mcp-client/src/registry.ts:144-148`; `src/mcp.ts:373`
- Severity: medium
- Kind: security
- Confidence: confirmed (the drop and its effect); that native WebMCP would coerce the value to `true`: plausible
- `validateTool` keeps only annotations whose value is a boolean. `annotations: { consequentialHint: "true" }` or `1` (plain JS, the CDN build, a JSON config) registers without an error, and `decideAndRun` then sees no `consequentialHint === true`: no confirmation, no `destructiveHint` to the AI app. This is recorded (DEC-051, "Only boolean annotations are kept", not an owner decision) and `test/registry.test.ts:197-204` asserts exactly the unsafe case. It fails open on the one run-time brake.
- Suggested change: reject a non-boolean value of a known hint with a `TypeError` (at least `consequentialHint`); keep ignoring unknown keys. Same for `RegisterToolOptions.webmcp`, which `register()` passes on unchecked.

#### 3. Result mapping: any object with a `content` array passes as a `CallToolResult`, a tool's `_meta` is overwritten, `Date`/`URL` become a string `structuredContent`

- Where: `packages/tab-mcp-client/src/mapping.ts:78-80`, `:90`; `src/mcp.ts:494-500`
- Severity: medium
- Kind: correctness
- Confidence: confirmed (what is sent); how each AI app treats invalid blocks: plausible
- `toCallToolResult` passes through every object whose `content` is an array (DEC-023). A domain object qualifies: a ProseMirror/TipTap document is `{ type: "doc", content: [{ type: "paragraph", … }] }`, a note is `{ title, content: ["…"] }`; the AI app gets content blocks that are not MCP blocks and a strict client rejects the whole response instead of reading a result. `result()` spreads the value and then sets `_meta`, so a passed-through result's own `_meta` never arrives. `isPlainObject` is true for any non-array object, so a returned `Date` or `URL` is sent as `structuredContent: "<string>"`.
- Suggested change: pass through only when every `content` item is an object with a string `type`, else take the JSON path; merge `_meta` (`{ ...value._meta, [serverInfo]: … }`); set `structuredContent` only for objects whose prototype is `Object.prototype` or `null`.

#### 4. `newAddress()` revokes nothing while disconnected; the takeover flag lives only in memory and the take-back uses whatever secret storage holds now

- Where: `packages/tab-mcp-client/src/tab-mcp.ts:569-597`, `:509` (`#secrets.get()`)
- Severity: low
- Kind: security
- Confidence: confirmed
- `#renew` sends `grants.revokeAll` only when `state === "connected"`; otherwise it only overwrites the local secret, and the old address keeps its grants at the relay (up to 90 days) for anyone who holds a copy of the old secret, which is the case "New address" exists for. `#takenOver` is lost on a reload, the natural reaction to "Another tab or program took over this page", and with two tabs a rotation in the other tab makes the take-back connect with the new secret, so the hijacked address is never taken back. The default dialog is fine (it connects first); a page with its own UI and the documented "call `newAddress()` on logout" are not.
- Suggested change: whenever a stored secret exists, take the address back with `hello.revokeAll` (the path of line 576) before rotating, with the secret captured at that moment. That also removes `#takenOver` and the `grants.revokeAll`-then-`bye` branch.

#### 5. Sibling detection counts `claimed` messages that cannot have caused the replacement

- Where: `packages/tab-mcp-client/src/connection.ts:160-165`, `:178-179`; `src/tab-mcp.ts:263`
- Severity: low
- Kind: security
- Confidence: confirmed
- The channel listens from `openConnection` on and `at` is never reset, and the message carries nothing to match. A claim heard while this connection was still opening (tab B's session accepted, then this tab replaces B) makes an impostor's takeover within the next 10 s report `sibling: true`. So does a claim from a tab on another address under the same key: after `newAddress()` in another tab, with storage that is blocked (memory secrets, but `#tabs` is set unless `storage === null`), and the `sessionStorage` case DEC-095 already names. All make "program took over" read as "Opened in another tab".
- Suggested change: ignore claims until the own `session` arrived, and post the address id (`addressIdOf`, already computed, not secret to same-origin script) in `claimed` and compare it. Closes all four cases in about five lines.

#### 6. `hello` sends `document.title` to the relay, which never reads it

- Where: `packages/tab-mcp-client/src/connection.ts:71-75`, `:433-438`; `packages/tab-mcp/src/protocol.ts:326-341`, `packages/tab-mcp/src/session.ts:303-308`

- Kind: security (privacy) / simplification
- Confidence: confirmed (`#hello` takes `secret`, `library`, `app?.name`, `revokeAll`; nothing in the relay's `src` reads `page`)

- Suggested change: send `page: { title: "" }` now (relays validate the field), make `page` optional in the protocol and drop it later. About 8 lines in the client, 5 in the relay.

#### 7. The client ignores `limits.maxBodyBytes`: an oversized result is serialised and queued whole, and `toolcallend` says `ok` while the AI app gets `-31006`

- Where: `packages/tab-mcp-client/src/serve.ts:137-150`; `src/connection.ts:321-334` (only `maxMessageBytes` and `heartbeatMs` are read); relay `packages/tab-mcp/src/exchange.ts:365-379`
- Severity: low
- Kind: correctness
- Confidence: confirmed

#### 8. A served port has none of the relay's limits

- Where: `packages/tab-mcp-client/src/serve.ts:280-325`, `:174-176`
- Severity: low
- Kind: security
- Confidence: confirmed (no cap in `servePort`/`createTunnel`); the effect on the dialogs: plausible, the UI reviewer's

#### 9. `createTunnelFetch` accepts a `requestTimeoutMs` that `setTimeout` cannot keep

- Where: `packages/tab-mcp-client/src/tunnel.ts:125-134`, `:225-231`
- Severity: low
- Kind: correctness

#### 10. Reconnecting can stop for good after a `connect()` from a `statechange` listener; `#pageWaits` is read by the wrong attempt

- Where: `packages/tab-mcp-client/src/tab-mcp.ts:635-664`, `:480-490`

- Kind: correctness

#### 11. Close codes 1001, 1011, 1012 and 1013 end reconnecting; the waits have no jitter

## Client library: UI, API and React

#### 1. Stacked confirmations: the Allow delay does not restart when a dialog becomes the top one

- Where: `packages/tab-mcp-client/src/ui.ts:425-457`, `packages/tab-mcp-client/src/mcp.ts:383`

- Kind: ux (safety design)

#### 1. A page that does not answer blocks the bridge for every tab

- Confidence: confirmed (code path); the attacker is the compromised renderer that A13 itself names

A page with a compromised renderer can answer `webmcp-list` with `origin: "https://bank.example"`. Its tools then carry the bank's origin for the AI app, the question says "Site (verified) <https://bank.example>", and tools the user allowed on that origin run for the attacker's same-named tool without a question. A13 says such a page "can neither … nor allow its own tools", and `question.ts:4` says "what Chrome reports". Navigation questions do use `tab.url` (`navigation.ts:351`).
- Suggested change: in `PageToolBridge.#read`, take the origin from `chrome.tabs.get(tab.id).url` after the list and refuse the list if it differs from `tools.origin`, or drop `origin` from the message.

#### 5. A new question moves "Allow all" and the tool switches under the pointer without a guard

- Where: `src/sidepanel/main.ts:241-267` (`showQuestions`), `src/sidepanel/index.html:11`
- Severity: low
- Kind: security
- Confidence: confirmed
- `#questions` is the first block of the panel, in flow. `movedUntil` is set only when a card is removed or when "Allow all" changes; a card that is added shifts the whole panel down by its height with every switch live. A click aimed at a lower switch or at "Allow on all sites" can land on "Allow all" or another tool's "asks first", which allows it for that origin for every paired AI app until taken back. The AI app chooses when its calls arrive.
- Suggested change: set `movedUntil = now + ALLOW_DELAY_MS` when a card is added too (one line), or show questions in a fixed overlay so nothing below moves.

#### 6. Size limits: the result budget exceeds what the relay carries, and page strings reach the worker uncut

- Where: `src/worker/bridge.ts:37-40`, `src/content.ts:74-79,244`, `src/tabs.ts:192-198`
- Severity: low
- Kind: correctness
- Confidence: confirmed (relay limit read in `packages/tab-mcp/src/session.ts:83` and `exchange.ts:365`; default 1 MiB)
- The bridge lets through 32 images of 1 MiB base64 each, but the relay fails any response body over `maxBodyBytes` (equal to `maxMessageBytes`, 1 MiB by default) with 502. A single maximum-size image never arrives, and the "each image up to 1 MB" in A13 is not reachable on the default relay.
- The content script returns `executeTool`'s string uncut. Over Chrome's 64 MiB message limit the send rejects and is reported as "The page changed or closed during the call" (`gone`), which sends the AI app to re-list tools.
- `document.title` and `lang` are not cut. A 2 MB title makes `page_info` and every navigation result fail at the relay and rides in every panel state.
- Suggested change: cut the title and language in `pageInfo` (about 300 characters); refuse a result over a fixed size in the content script with its own error; set the image budget from the session's `maxBodyBytes` or lower the documented figure.

#### 7. Test hooks ship in the store build

- Where: `src/background.ts:185-189`, `src/sidepanel/main.ts:432-433`; `scripts/build.ts:248` (`storeProblems` does not look for them)
- Severity: low
- Kind: quality
- Confidence: confirmed
- `tabMcpNotificationButton`, `tabMcpNotificationDismissed` and `tabMcpNotificationClicked` are put on the service worker's global object in every build. They answer a question (Allow, Always allow) from a `Runtime.evaluate`. No page or other extension reaches the worker's globals, and a DevTools client could click the panel anyway, so this is no escalation, but it is an answer path that exists only for tests in the package that goes to the store.
- Suggested change: define them only in the `--test` build (`define: { TAB_MCP_TEST: "true" }` in `Bun.build`, dead-code-eliminated otherwise), and let `storeProblems` fail when `background.js` contains `tabMcpNotification`.

#### 8. `page_info` hands the full address, query and fragment included, to any paired AI app without a question

- Where: `src/content.ts:76` (`url: doc.location.href`), `:154`; `src/worker/tools.ts:44-51`
- Severity: low
- Kind: security
- Confidence: confirmed
- `page_info`, `webmcp_tools` and every navigation result carry `location.href` as it is. With "Allow on all sites", a paired AI app (and the relay) can read the address of whatever tab is in front at any time. That includes magic links, password-reset links, OAuth callbacks with `code=` or `#access_token=`, and search queries. The listing declares "Web history", so the claim is kept; PRIVACY.md and A13 do not say that the query and fragment are included.
- Suggested change: say so in PRIVACY.md and A13. If the fragment is not needed, send `origin + pathname + search` only.

#### 9. The optional host permission is wider than what the extension acts on

- Where: `scripts/build.ts:125` (`optional_host_permissions: ["<all_urls>"]`), `src/background.ts:75`
- Severity: low
- Kind: security
- Confidence: confirmed for the manifest; reading `file:` pages also needs the user's "Allow access to file URLs"
- "Allowed", "Always allow" and the navigation rules treat only http(s) origins as sites, but `<all_urls>` also registers the content script on `file:` pages. `page_info` then sends local paths and titles. The manifest also leaves `incognito` at its default, so a user who allows the extension in Incognito gets those tabs offered through the same connection.
- Suggested change: `optional_host_permissions` and the registered `matches` as `["http://*/*", "https://*/*"]`, and `"incognito": "not_allowed"` unless Incognito tabs are meant to be bridged.

### Could be deleted or simplified

- **The question's own window**: `src/worker/question-windows.ts` (127 lines), `src/question/*` (78), `isQuestionSender`, `parseQuestionAnswer` and the port constants in `protocol.ts` (about 45), the glue in `connection.ts` and `background.ts` (about 85), one build entry, plus tests; about 340 lines and a second answering channel to keep safe. ### Looked at and found sound

- **Who may talk to the worker**: the panel port (extension page, no tab, exact path), the question port (only a window the worker opened, only its question), and one content-script event. No `externally_connectable`, no external listeners, no `web_accessible_resources`.
- **Extension pages**: default MV3 CSP, no inline or remote script; every page-supplied or AI-app-supplied text goes through `textContent`; the one link is static with `rel="noopener"`; setup commands only for shell-plain addresses.
- **Content script**: isolated world, so prototype tampering does not reach it. DOM clobbering of `document.modelContext`, `title` or `documentElement` only breaks that page's own listing; `location` cannot be clobbered. The sender id is checked; top frame only.
- **Tools offered twice**: `data-tab-mcp-webmcp` hides only the page's own tools, at list and at call time; the names sent are capped.
- **Tool listing as an injection channel**: `page_` prefix with a fixed alphabet, own-tool names and clashes left out, origin prefix, cuts, `untrustedContentHint` on every tool.
- **Call path**: document id and read-only claim checked in the page; the library refuses a tool unregistered while the question was open; Always allow is keyed by grant, origin, document and tool, checked again after the answer, and dropped synchronously on unregister. `webmcp_call` confirms like `page_<name>`.
- **ReDoS guard**: covers `pattern`, `patternProperties` and `propertyNames` (but see finding 2).
- **Questions**: 750 ms focus guard in panel and popup, 500 ms on notification buttons, per-notification ids, the removal guard, 5 per AI app, invisible characters escaped, the client name capped at 64 by the relay. Allow from a notification with cut arguments is the owner's recorded decision, not reopened.
- **Navigation**: one URL parser for the check and the address handed to Chrome (http(s) only, no userinfo, backslash and tab tricks normalised, punycode shown, host cut from its start); origin and tab-in-front checked again after the question; back and forward from the Navigation API in the isolated world. The open redirect and same-origin GET are recorded residuals (DEC-121).
- **Storage and connection**: IndexedDB in the extension's origin, no `storage` permission, the secret keyed per relay origin, Always allow in memory only, takeover kept across restarts, AI access on only from the panel or a start with it left on, pairing codes only while a pairing view is open.
- **Build**: the key only in the development build, `--zip` only with `--store`, the manifest read again from disk before packing (no key, no `host_permissions`, no `.map`), the output directory emptied first, reproducible zip.
- **Privacy statements**: nothing leaves with AI access off; the only `fetch` is the extension's own icon; no analytics; what is stored matches the code (apart from findings 3 and 8).

## tab-mcp for Chrome: code quality and UX

Extension review (quality, correctness, UX, overengineering) of packages/tab-mcp-extension: 22 findings, all from reading the code; nothing was run.

"Confirmed" = code path read end to end. Paths are relative to `packages/tab-mcp-extension/` unless they start with `packages/` or `kb/`.

### 1. Findings

#### 1. `webmcp_tools` gives no input schemas, so `webmcp_call` arguments are guesswork

- Where: `src/worker/bridge.ts:179-205`, `src/worker/bridge.ts:538-546`, `src/worker/tools.ts:52-89`
- Severity: high
- Kind: correctness
- Confidence: confirmed
- `webmcp_tools` returns `BridgeState`, whose `Offered` entries carry name, tool, title, description, readOnly and problem, but no `inputSchema`. `webmcp_call` exists for the apps that read their tool list once (Claude, Codex, per `kb/design/extension.md:107`), so for every page other than the one in front at connect time they never see a schema. `webmcp_call` then says the arguments must match "its inputSchema" and rejects with the first three validator errors. The plan says otherwise: `kb/iterations/iteration-20-webmcp-bridge.md:18` ("names, descriptions and schemas").
- Suggested change: keep the compiled schema on `Offered` (it is already built in `#read`) and return it from `webmcp_tools`; the 16 KB per-schema and 64-tool caps already bound the size.

#### 2. An AI app running in the same Chrome profile becomes "the tab in front"

- Where: `src/tabs.ts:42-68`
- Severity: medium
- Kind: ux
- Confidence: confirmed
- `tabInFront()` takes the active tab of the last focused normal window and excludes only the extension's own pages. A user who types in claude.ai or chatgpt.com in that profile (same or another window) has just focused that tab, so `page_info` answers with the chat page, and the target page's `page_<name>` tools are unregistered at that focus change. The panel's setup steps name Claude and ChatGPT without saying this; the README only says "outside the browser".
- Suggested change: in `usable`, skip tabs whose host equals a paired grant's `client.host` (falling back to the most recently used other tab, as for own pages). Otherwise say in the pairing box that the chat must run in the desktop app, another browser or another profile.

#### 3. The panel says "AI access is off" while the extension keeps reconnecting every minute

- Where: `src/worker/connection.ts:736-747`, `src/worker/connection.ts:383-396`, `src/worker/connection.ts:806-820`
- Severity: medium
- Kind: correctness
- Confidence: confirmed
- Status comes only from the library: disconnected and not `reconnecting` is "off". With the WebSocket down the worker idles and stops; the next start (alarm, or the open panel's port reconnecting) calls `#connect()`, a first connect that the library does not retry (`packages/tab-mcp-client/src/tab-mcp.ts:945-951` schedules reconnects only after an established connection closes). So about 30 s into an outage the panel flips from "Connection lost · retrying" to "AI access is off", switch off, "Turn on AI access", no badge. `aiOn` is still true, `keepUp()` retries each minute, and access comes back without a click. The unchecked switch cannot even send `stop`.
- Suggested change: put `aiOn` into `PanelState`; when `aiOn && !replaced` and the library is disconnected, report "retrying" (switch on, badge "…").

#### 4. A question that times out, or is refused as "busy", reaches the AI app as "The user declined" on `page_<name>` tools

- Where: `src/worker/decide.ts:57-65`, `packages/tab-mcp-client/src/mcp.ts:381-393`, `packages/tab-mcp-client/src/tab-mcp.ts:835-842`
- Severity: medium
- Kind: correctness
- Confidence: confirmed
- `decide` throws for "timeout" and "busy". On the `webmcp_call` path the message passes through. On the `page_<name>` path the library catches a throwing `onConfirm` as `false` and answers "The user declined", also for "busy", where the user was never asked. Iteration 26 says the AI app is told the user did not answer. Client 0.14.0 has `"unanswered"` for this; the extension never returns it, and `test/worker.test.ts:824-834` pins the throwing.
- Suggested change: `decide` returns `ConfirmAnswer`, with `"unanswered"` on timeout; `callByName` maps it to its own error. For "busy", either return `"unanswered"` too or let the bridged tools ask inside `execute`, as the navigation tools do.

#### 5. "Always allow" is lost on any tab switch, not "until the page changes"

#### 11. The side panel loses keyboard focus on every state message, and other accessibility gaps

### 3. Looked at and found sound

- **Listener registration** (`background.ts`): all at top level, synchronously; a notification click keeps its gesture; a restarted worker clears stale notifications before any handler can answer one.
- **Keepalive:** the relay's ping is an application message answered with `pong`, which resets the idle timer; the alarm covers a stopped worker (but see 3 and 14). The 25 s versus 30 s margin is thin, but DEC-116's spike measured it.
- **Panel commands:** serialised on one promise chain, so connect then stop, and two "allowed" writes, cannot interleave.
- **Bridge refresh:** single flight with one re-read; abort then re-register under the same name is synchronous in the registry; a registration the library refuses is removed from `webmcp_call` too.
- **Calls:** bound to the listing document and read-only claim in the content script; a navigation mid-call ends as "gone"; the 60 s timeout and cancel always end the call.
- **Confirmation paths:** the library asks only for `consequentialHint`, so `webmcp_call` and the navigation tools do not double-ask.
- **Questions:** first answer wins, clear-after-create, per-app cap, cancel by the AI app, panel closed or covered goes to a notification.
- **Navigation tools:** origin re-check and in-front re-check after the question; `waitForLoad`'s quiet path for same-document steps.
- **Storage:** `kv.ts` transaction handling and reopen; `CachedSecretStorage` write ordering; secrets are keyed per relay origin by the library.
- **Content script registration:** `syncRegistration` on install, startup and permission changes; `ask()` re-injects on demand.
- **Reuse of the client library:** connection, MCP handler, protocol types, setup steps and `escapeInvisible` are imported, not copied; the own confirmation UI is justified by the worker having no document.
- **Not examined:** incognito (spanning mode), prerendered pages and bfcache restores. No code or test mentions them.

### Findings

#### 1. The dedupe attribute hides a tab-mcp page's tools from the extension even when the AI app is not paired with the page

- Where: `packages/tab-mcp-extension/src/content.ts:69,89-99,152,171,229`; `packages/tab-mcp-extension/src/sidepanel/main.ts:393`; `packages/tab-mcp-client/src/webmcp.ts:70-81`
- Severity: medium
- Kind: webmcp
- Confidence: confirmed
- The extension drops every name in `<html data-tab-mcp-webmcp>`, assuming the AI app reaches those tools through the page's own address. It cannot know that. Scenario: WebMCP flag on, a ractive.ch example open, AI app connected only to tab-mcp for Chrome. `page_info` reports `webmcp.tools: 4` (it counts `getTools().length`, mirrors included), `webmcp_tools` returns `tools: []` plus an unexplained `mirrored: [...]`, `webmcp_call` answers "offers no tool", and the panel says "4 more come from the page's own tab-mcp connection", which does not exist.
- The attribute is also read only from the top document, while `getTools()` lists same-origin frames too (draft and Chrome docs). A mirror in a same-origin iframe is therefore not deduped, and the top page's list hides same-named frame tools.
- Suggested change: drop the dedupe. An app connected to both then sees `list_todos` and `page_list_todos` under two connectors, and a consequential tool registered with `{ webmcp: true }` asks twice. If kept, make `page_info` count the same set and have `webmcp_tools` and the panel say "offered by the page itself only if your AI app is connected to it".

#### 2. A page tool that navigates the tab is reported to the AI app as a failure; the `null` branch is untested against Chrome

- Where: `packages/tab-mcp-extension/src/tabs.ts:192-198`; `packages/tab-mcp-extension/src/worker/bridge.ts:160-162,314-319`
- Severity: medium
- Kind: webmcp
- Confidence: plausible (code path confirmed; Chrome's timing unverified)
- `executeTool()` is awaited in the content script of the document that navigates. When that document unloads, `sendMessage` rejects and `callInTab` returns `gone`, so the AI app gets an `isError` result: "The page changed or closed during the call…".
- The success text for `null` ("The tool started a navigation") is reached only if Chrome resolves with `null` and the reply leaves before unload. The spike never observed this, and only `resultOf(null)` has a unit test.
- Navigating tools (`proceed_to_checkout`, search) are the main kind on the Shopify storefronts the design note names as the target. An AI app told "failed" may retry a checkout.
- Suggested change: treat a channel closed mid-call as "the page navigated during the call; the tool may have completed", not an error, and answer with the new page's `page_info` as the navigation tools do. Add an end-to-end test with a tool that calls `location.assign()`.

#### 3. `outputSchema` is in the draft's `ModelContextTool` and `RegisteredTool`; the library's `Tool` has no such field and drops it silently

- Where: `packages/tab-mcp-client/src/types.ts:120-131`; `src/registry.ts:98-157`; `src/mcp.ts:502-513`; `src/webmcp.ts:111-120`; `kb/research/webmcp-register-tool.md`
- Severity: medium
- Kind: webmcp
- Confidence: confirmed (draft of 2026-11-12; Chrome 156 dropping it is the project's own canary)
- "A tool in the WebMCP shape" no longer holds. A draft-shaped tool literal with `outputSchema` is a TypeScript excess-property error; from JavaScript `validateTool` discards the field.
- It then reaches neither MCP `tools/list` (MCP has `outputSchema`, and the library already sends `structuredContent`) nor the native registration.
- The extension's `PageTool` and the canary's key list (`test/webmcp-spike/webmcp.test.ts:65-73`) assume Chrome has none. The canary will fail when Chrome adds it, which is the intended signal, but nothing is prepared.
- Suggested change: add `outputSchema?: JsonSchema` to `Tool` (JSON-copied like `inputSchema`), emit it in `listTools()`, pass it in the mirror, and carry it through `PageTool` and the bridge when present. Update the research note's IDL.

#### 4. A mirrored tool that returns `undefined` is a failed call under the draft

- Where: `packages/tab-mcp-client/src/mcp.ts:456`; `src/mapping.ts:77`
- Severity: medium
- Kind: webmcp
- Confidence: plausible (draft text confirmed; Chrome 156 unverified; no test)
- Through the relay a void `execute` is a valid empty result (`{ content: [] }`). Through WebMCP `webMcpCall` resolves with `undefined`.
- The draft serializes the result with "serialize a JavaScript value to a JSON string", which throws for `undefined`, giving "unserializable result" and an `OperationError` rejection. The agent sees a successful side effect as a failure and may repeat it.
- No tool in `webmcp-browser.test.ts` returns `undefined`.
- Suggested change: in `webMcpCall`, resolve `undefined` as `null` or a fixed string such as "Done." (lazy chunk, no core bytes). Add a browser test with a void tool.

#### 5. Tools marked only with MCP's `destructiveHint` are mirrored by default and reach in-browser agents with no hint at all

- Where: `packages/tab-mcp-client/src/tab-mcp.ts:275`; `src/webmcp.ts:63-68,106-110`; `ractive.ch:src/tab-mcp/diagram/main.ts:929-943`
- Severity: medium
- Kind: webmcp
- Confidence: confirmed
- The default exclusion keys on `consequentialHint` alone, and the mirror forwards only the four WebMCP hints. DEC-022 maps `consequentialHint` to `destructiveHint`; nothing maps back.
- The live diagram editor's `delete_elements` (`destructiveHint: true`) is registered natively with empty annotations, so an unpaired in-browser agent sees it as an ordinary tool.
- The rule is also not the extension's: the mirror asks only for consequential tools, while the extension asks for everything not read-only.
- Suggested change: treat `destructiveHint: true` like `consequentialHint: true` for the mirror's default (left out unless `{ webmcp: true }`), and set `consequentialHint: true` on the native registration when it is mirrored. Document it next to DEC-022.

#### 6. MCP-style return values go out to WebMCP as the JSON of the wrapper, including base64 images

- Where: `packages/tab-mcp-client/src/mcp.ts:454-456`; `ractive.ch:src/tab-mcp/diagram/main.ts:974-990`
- Severity: medium
- Kind: webmcp
- Confidence: confirmed (code path; the browser JSON-encodes whatever `execute` resolves with)
- `webMcpCall` hands the browser what `execute` returned. For a tool that returns `{ content: [...] }`, the in-browser agent gets `{"content":[{"type":"text","text":"…"}]}` as text.
- For the live `get_image` (read-only, so mirrored) it gets a whole PNG as base64 inside JSON text: tokens for nothing, since WebMCP results are strings.
- The extension unwraps exactly this shape on the way in (`resultOf`); the mirror does not on the way out.
- Suggested change: in `webMcpCall`, when the value is a `CallToolResult`, resolve with `structuredContent` if present, else the joined text blocks (`resultText` exists), and replace non-text blocks with a short note. On ractive.ch, register `get_image` with `{ webmcp: false }`.

#### 7. The bridge relies on Chrome returning string results unquoted; the draft says every result is JSON-serialized

- Where: `packages/tab-mcp-extension/src/worker/bridge.ts:160-176`
- Severity: low
- Kind: webmcp
- Confidence: plausible (draft confirmed; Chrome 156 unquoted per the canary; future Chrome unknown)
- The draft's "invoke the execute callback" serializes any fulfilled value `v` to a JSON string, so `"Hello"` becomes `"\"Hello\""`. Chrome 156 returns it as is.
- If Chrome aligns, every plain-text result reaches AI apps wrapped in quotes with escaped newlines. `resultOf` only looks for a leading `{`.
- The canary (`test/webmcp-spike/webmcp.test.ts:93-96`) would catch it, but the divergence is not recorded in `kb/research/webmcp-from-extension.md`.
- Suggested change: record it in the research note. In `resultOf`, also try `JSON.parse` on a value starting with `"` and use the result when it is a string.

#### 8. What a page tool loses through the extension compared with page to relay

- Where: `packages/tab-mcp-extension/src/content.ts:192-196`; `src/worker/bridge.ts:82-114,160-176,495-499,606-612`

#### 9. The mirror's retry handles a case the draft rules out

#### 10. Capturing the getter at module load and the `instanceof ModelContext` check buy nothing the threat model claims, and can miss a late origin-trial token

- Where: `packages/tab-mcp-client/src/webmcp.ts:24-60`
- Severity: low
