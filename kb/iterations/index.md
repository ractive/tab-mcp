## iteration

* [Iteration 10: a stolen address secret](iteration-10-address-takeover.md) - What someone who copies a page's address secret can do, said plainly in the docs; a page that is taken over says so and offers a new address; and whether a backend-signed address claim is worth building.
* [Iteration 11: relay request path hardening](iteration-11-relay-hardening.md) - Fixes from the 2026-10-24 review of the relay's request path and sessions (packages/tab-mcp/src/relay.ts, exchange.ts, session.ts): an unbounded listen stream, idle timeouts that never come back, 401 without WWW-Authenticate, limits, shutdown answers, log hygiene.
* [Iteration 12: authorization server hardening](iteration-12-oauth-hardening.md) - Fixes from the 2026-10-24 security audit of the relay's OAuth, CIMD, OIDC and token store code: an owner locked out of /authorize, CIMD rate limits per registrable domain, OIDC flows per request, refresh-token retention, look-alike client names, small doc items.
* [Iteration 13: browser library fixes](iteration-13-client-hardening.md) - Fixes from the 2026-10-24 review of the browser library: the Allow delay in a background tab, argument spoofing with direction characters, Always allow, result and schema edge cases, a tool removed during its confirmation, two connect dialogs, React provider stability.
* [Iteration 14: CI, release and repository settings](iteration-14-ci-supply-chain.md) - Fixes from the 2026-10-24 supply-chain review: the Docker Hub token in the release environment, the release approval, Dependabot alerts and SHA pinning, Chrome in the client release job, pinned Chrome, job timeouts, source maps.
* [Iteration 15: private_key_jwt client authentication](iteration-15-private-key-jwt.md) - The relay's authorization server verifies private_key_jwt client assertions (RFC 7523) at /token and /revoke, for ChatGPT's connectors: CIMD jwks_uri under the SSRF rules, the assertion checks, a jti replay store in the token store, and grants bound to the method they were made with.
* [Iteration 16: feedback from the comparis game](iteration-16-game-feedback.md) - Fixes and developer-experience changes from integrating the React client into the comparis office game: dialog centring under CSS resets, the development public URL, a 'connection lost' label, published test helpers, typed tool inputs, and README sections.
* [Iteration 17: browser extensions as pages](iteration-17-extension-origins.md) - The relay accepts a Chrome or Edge extension's origin (chrome-extension://<id>) in TAB_MCP_ALLOWED_ORIGINS and TAB_MCP_SITES, so an extension can offer tools from its side panel; other extension schemes are refused with a reason.
* [Iteration 18: can an extension reach a page's WebMCP tools?](iteration-18-webmcp-from-extension.md) - A spike before the extension is built: a test page registers WebMCP tools, and a test extension tries to list and call them from a content script, from a script in the page's own world, and to register tools of its own; the findings decide the WebMCP bridge (iteration 20).
* [Iteration 19: the extension's skeleton](iteration-19-extension-skeleton.md) - packages/tab-mcp-extension: an MV3 extension whose side panel connects to a tab-mcp relay and offers one read-only tool about the tab in front (page_info, with whether the page has WebMCP on); build, test harness and CI after Overmark's.
* [Iteration 1: protocol and relay core](iteration-1-relay-core.md) - The relay's tab WebSocket, stable addresses, the token store, the HTTP tunnel with limits, timeouts and keep-alives, and the health endpoint, tested with a scripted tab and the MCP SDK client.
* [Iteration 20: a page's WebMCP tools for AI apps](iteration-20-webmcp-bridge.md) - When the page in front registers WebMCP tools, the extension offers them to the connected AI app through the relay, reached from its content script (DEC-113): listed, called with a timeout, kept in step with toolchange, results marked untrusted, consequential calls confirmed.
* [Iteration 23: releasing tab-mcp for Chrome](iteration-23-extension-release.md) - The Chrome Web Store listing, privacy policy and review notes, a release workflow on extension-v* tags that publishes the store package, and the documentation on ractive.ch/tab-mcp.
* [Iteration 24: can an AI app give a site tools through user scripts?](iteration-24-user-scripts-spike.md) - An experiment: an AI app writes a user script for the site in front, the user sees and allows it, and the extension runs it with chrome.userScripts so the script's functions become tools for the AI app. Finds out what Chrome and the Chrome Web Store allow, how the tools reach the AI app, and what it takes to keep it safe; decides whether it goes into the extension.
* [Iteration 25: tab-mcp tools also as WebMCP tools](iteration-25-client-webmcp-mirror.md) - When a page asks for it, the client library registers its tools also with document.modelContext.registerTool() where the browser has WebMCP, so agents in the browser (ChatGPT's browser, Gemini in Chrome when it comes, extensions) can use the page's tools; consequential tools only when the page says so per tool, because an agent in the browser can answer the page's own confirmation.
* [Iteration 26: the connection without the side panel](iteration-26-background-connection.md) - The connection to the AI app moves out of the side panel into the service worker (the relay's heartbeat keeps it running; no offscreen document), so it stays while the panel is closed and comes back after a restart; the side panel becomes a view with its own pairing and question UI. A tool that asks first asks in the side panel of the tab's focused window, else in a Chrome notification.
* [Iteration 27: navigation tools](iteration-27-navigation.md) - tab-mcp for Chrome gets four standard tools, navigate, go_back, go_forward and reload, for the tab in front it has access to; each returns the new page's page_info once it has loaded. Within the page's origin they run at once; to another origin they ask the user first (DEC-121), and the result says when the extension may not read the new page.
* [Iteration 28: the page's tools for the site's own agent, without a relay](iteration-28-tunnel-without-relay.md) - The client library serves its tools over any message port (mcp.serve), not only through a relay, and a small fetch function speaks the other end (@ractive-ch/tab-mcp-client/tunnel). A site's own agent, whose chat runs in an iframe on the page and whose backend already holds a WebSocket to that chat, then calls the page's tools with the same tab-mcp.v1 http.* messages, with no relay, pairing or address; relay is optional on TabMcp. Client only; the relay does not change.
* [Iteration 29: relay denial of service and the refresh bug](iteration-29-relay-dos.md) - Iteration A of the review of 2026-11-13: a token store failure during a refresh no longer costs the user their pairing (RQ 1), and the cheap ways for an unauthenticated party to stop pairing or park sockets are closed or bounded (RS 1 to 5, 8, 13, 15), with bounded timer settings (RQ 3), keep-alives only in event streams (RS 16 = RQ 9), a sweep that survives a throwing store (RQ 10) and an error handler for Bun.serve (RQ 20). Relay only; DEC-127 to DEC-129.
* [Iteration 2: browser library](iteration-2-client-library.md) - The tab-side library: a small eager core with WebMCP-style registerTool, and on connect() the lazily loaded connection and MCP handler, pairing UI and consequential-tool confirmation.
* [Iteration 31: the client's confirmation and registry](iteration-31-client-confirmation.md) - Fixes from the review of 2026-11-13 (iteration C): a non-boolean hint is refused instead of dropped, only real MCP results pass through (with their _meta), the schema check skips data, confirmations are shown one at a time and Allow waits until the arguments were seen, stray keys cannot refuse, the dialogs keep page colours and pointer-events out, and serve ends when its port closes.
* [Iteration 35: tab-mcp for Chrome, correct before the store](iteration-35-extension-store.md) - Iteration G of the review of 2026-11-13: webmcp_tools gives input schemas, the ReDoS guard keeps parameters named pattern, a stuck page no longer holds the bridge, the panel says "retrying" instead of "off", page tools say why a call did not run, the ephemeral Always allow gives way to "Don't ask again on <host>" (owner, DEC-139), mirrored tools are offered (DEC-140), a navigating page tool is no failure, the origin comes from Chrome, http(s) only and no Incognito, test hooks only in the test build, and the store listing and both privacy pages describe the navigation tools.
* [Iteration 32: client connection edge cases](iteration-32-client-connection.md) - Iteration D of the review of 2026-11-13 (CC 4, 5, 6, 7, 10, 11, 12, 14, 15). newAddress() always takes the old address back with hello.revokeAll, connected or not, and the take-back fallback for relays of 0.4 and older, #takenOver and #pageWaits are gone; sibling claims carry the address id; close codes of a restarting proxy reconnect, with jitter; an oversized result becomes an error result before toolcallend; hello no longer sends the page title and the relay ignores page; the tab no longer answers frames it cannot read. Client, plus a few lines in the relay.
* [Iteration 33: the connect dialog for people who are not developers](iteration-33-connect-dialog.md) - Iteration E of the review of 2026-11-13 (CU 4, 6, 7, 9, 12, 15, 23, CU 5 in part, CU 22). The connect dialog says in plain words why it is not connected and offers Connect again, follows reconnecting and identity binding, puts the help between the address and the code and New address apart with a line on what it does; the setup steps end with the sign-in step; a refused Copy says so on the button; a confirmation in a hidden tab marks the tab's title and consequential tools say in tools/list that the user confirms in the page's tab; the dialogs carry lang and dir; the code row fits 320 px. The guide on ractive.ch gets pages without a code and three answers.
* [Iteration 3: OAuth authorization server with pairing](iteration-3-oauth.md) - Our own authorization server: metadata, CIMD client validation, pairing codes typed on the authorize page, token endpoint with PKCE and rotating refresh tokens, revocation, spec tests, conformance runs and a security review.
* [Iteration 4: calculator example and end-to-end tests](iteration-4-calculator-e2e.md) - The four-function calculator page as the minimal example, an automated browser end-to-end test, a headless Claude Code run, and the first compatibility matrix.
* [Iteration 5: packaging, documentation and release](iteration-5-packaging-release.md) - npm builds with declarations, trusted publishing with provenance, the multi-arch Docker image, project documentation, the developer skill, dependency updates and the token-expiry warning.
* [Iteration 6: deployment documentation and examples](iteration-6-deployment-bunny.md) - Generic, secret-free deployment docs and examples for running a tab-mcp relay (Docker, a bunny.net Magic Containers example); the owner's ractive.ch instance is deployed from the private ractive/ractive.ch repository.
* [Iteration 7: identity binding (0.2+)](iteration-7-identity-binding.md) - Binding a tab and an AI app to the same OpenID Connect identity, as a second pairing method next to the code.
* [Iteration 8: the relay's answer when the page is not open](iteration-8-page-not-open.md) - When the page is not open, the relay waits a short grace period for it and then answers with HTTP 200 and a JSON-RPC message instead of 503, so an AI app's connector keeps its session.
* [Iteration 9: React bindings for single-page apps](iteration-9-react.md) - A React entry point of the browser library (`@ractive-ch/tab-mcp-client/react`) with a provider, state and tool hooks and a connect button, plus automatic reconnecting in the core library, for SPAs that have no server to host an MCP server.
